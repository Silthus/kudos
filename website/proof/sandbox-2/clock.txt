WS36 on an open leaderboard: the board turns over on the first clock tick after the viewer's midnight,
with the page held open. #134's follow-up, run here.

Disposable local backend on 127.0.0.1:4410/4411 (instance kudos-i136), deployed from this ticket's tree.
The mock Slack issuer ran on 4412 with MOCK_FLAGS_ON=everyone-board,xp-levels, a local override only.
No cloud deployment was used.
The browser was signed in with a proof session (users, authSessions and authRefreshTokens rows imported on
that backend; see README.md).
The website clock's cron ticked at :01:44, :16:44, :31:44 and :46:44 past each hour (first tick at
deploy, 00:31:44Z).

Each viewer gave 2 kudos on Tuesday 2026-10-06, 5 on Wednesday 2026-10-07, and 11 this week, so G18's
line depends on the viewer's day:
  - on Tuesday 2026-10-13 it compares with last week up to Tuesday: 11 - 2 = 9;
  - from Wednesday 2026-10-14 it compares up to Wednesday: 11 - 7 = 4.
An observer in the open page logged every change of that line with the browser's time.
The browser's clock and the host's agreed within 0.2 s (checked at 01:02:51Z).

  The page turned a minute before the clock ticked. The PostHog component re-reads flag definitions
  every minute. The mock answers without an ETag, so each read rewrote the cached row (fetchedAt 01:02:44Z,
  then 01:03:44Z). Every query that reads a flag, getLeaderboard included, then re-ran at :44, and the first
  re-run after midnight computed the new day. On the sandbox and in production the cached row changes
  only when the definitions do: both still held fetchedAt 2026-10-13T21:33Z at 00:25Z on 2026-10-14. So
  run 1 shows the open page turning over, but not that the clock tick alone turns it.
