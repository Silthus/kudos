# Quests start on two paths, and the Monday path never reads Unlocks

Quests used to start only when the unlock path opened the `quests` feature, and each Journey step started when its feature opened. Now one gate, `questsFor`, says which path a member is on: `monday` (the `monday-quest` and `xp-levels` flags) or `unlocks` (today's `questsApplyTo`), and Monday wins when both hold. `startQuests` is the only writer of a Monday-path member's start, once: the welcome on a hug or a received kudos, Quests' own `kudosGiven` subscriber for a giver with no start whose kudos says why, the catch-up and the weekly sweep for a member welcomed before this shipped call it, each after reading `monday-quest` with an exposure. On the Monday path the onboarding quests (first-thanks, someone-new, two-days) all start together, and the weekly draw and the onboarding quests read the stored start instead of the `quests` feature's opening. Neither reads Unlocks, the Book or the store. The unlock path's start stays its `quests` opening, so no stored start is backfilled and nothing on that path moves.

We kept `questsApplyTo` meaning "on the unlock path" instead of widening it to both paths. About twenty callers read it for coin lines, crates, swaps and group copy, and widening it would light those up for Monday members. Only the readers the feature needs move to `questsFor`. This bends the quests exception in [ADR-0006](0006-unlocks-gate-what-members-see-not-what-they-earn.md): opening the feature is now one way to start quests, not the only one.
